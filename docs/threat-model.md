# Showcase trust boundaries

| Boundary                  | Trusted input                                          | Enforcement and failure evidence                                                                                                            | Remaining boundary                                                                   |
| ------------------------- | ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| Browser → API             | Server session; generated CSRF token                   | HttpOnly/Secure production cookie, same origin, rate limit, real CSRF request specs, owner 404                                              | Session key rotation logs everyone out; not a multi-device revocation service        |
| Operator → Publishing     | Appointed operator and owned integration               | Owner scope in reads/diagnose/reconcile/private artifact; signed owner/kind cursor                                                          | Operator appointment is administrative; register API never permits this attribute    |
| Partner → callback        | Exact signed raw body and event/timestamp              | HMAC, expiration, replay conflict, immutable receipt, monotonic sequence                                                                    | Callback secrets require coordinated rotation; only current key is accepted          |
| ZIP → validator/storage   | Digest-bound manifest under a versioned policy         | Bounded request/expanded bytes/count, traversal/duplicate/mismatch checks, real ClamAV, digest on publish/download                          | 2 MB cap is deliberate; this is not arbitrary binary game distribution               |
| API → remote partner      | Administrator-approved origin and credential reference | TLS/hostname verification, time budgets, response bounds, no redirects, no automatic POST replay                                            | Origin approval owns DNS/network trust; arbitrary user destinations are forbidden    |
| Upload → cleanup          | Durable intent state and age                           | Claim fencing, dry-run, reference checks, tombstone SQL guards                                                                              | Uploading leases are preserved; grace must cover backup retention                    |
| Code → registry → runtime | Successful main release and signed hosted builder      | Full source/history secret scan, canary, immutable manifest, Trivy, provenance source/repo/workflow checks, false-revision negative control | A trusted maintainer can change the builder; provenance is not proof of correct code |
| Migration → runtime DB    | Separate privileged migration identity                 | Runtime cannot CREATE schema/table or mutate protected history; direct SQL denial probe                                                     | Application runtime can write permitted business rows; constraints remain essential  |
| Backup → restore          | Recovery key held separately from snapshot             | GCM authentication before tar extraction, dump/byte hashes, count checks, lookup-only recovery                                              | Local key directory is not an independent custody/offsite service                    |
| Metrics → receiver        | Loopback/private networks and internal tokens          | Bounded labels, authenticated receiver, retained timeline and silences                                                                      | Active alerts are resent by Prometheus after restart; one local node is not HA       |

Credential rotation regression: an old validation cannot authorize a new publish after rotation; an existing unknown operation can be looked up under the new credential without another publish; an old callback signature fails and current-key replay is deduplicated. The test uses a gateway double to inspect the boundary; the real partner lost-response scenario is separate.

Published Trivy history produced 24 false positives: public GitHub commit SHA-1 URLs in two exact Grafana reports resembled a legacy Sourcegraph token. The exception matches only those URL lines/paths and preserves the default rule plus a generic-key canary. Runtime keys, DB dumps, Docker auth and recovery keys are never part of evidence uploads.

After preserving hosted evidence, the same generic-key rule also flagged a diagnostic command_key UUID in the new Publishing summary. Its exception applies only to that exact file and a UUID-shaped command_key match; it does not allowlist other fields or authentication tokens. The canary still must be detected.

References: [GitHub attestation action](https://github.com/actions/attest), [verification identity flags](https://cli.github.com/manual/gh_attestation_verify). Registry attestations bind builder identity and source digest; their predicate fields do not independently certify security, test completeness or SRE guarantees.

A local recovery report placed a source SHA-256 next to an API-related filename, triggering generic-key detection. New metadata separates file and sha256 fields. Only the exact historical filename/checksum line in that exact report is excepted for history scanning; credentials in other fields remain detectable.
