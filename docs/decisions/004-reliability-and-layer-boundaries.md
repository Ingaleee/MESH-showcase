# Reliability acceptance and dependency boundaries

Scope: MESH-showcase only. This is the specification for the next execution, not evidence that it passed.

The backend is a modular Rails monolith. Existing ActiveRecord services are not framework-independent application code. We introduce a strict Domain → Application → Infrastructure boundary for the external publication execution path, retaining the existing public facade and SQL guarantees. Domain owns decisions; Application orchestrates ports; adapters own locks, transactions, storage and HTTP. The composition root connects them. Other Rails use cases retain their documented coupling rather than being misleadingly relabelled.

Acceptance before measurement:

- Mixed workload: reads, authenticated commands, idempotent replays and durable notifications; an open arrival schedule, bounded client concurrency, explicit dropped arrivals, latency per class, PG waits/connections and container resources. Baseline 5 arrivals/s for 30s: no unexpected 5xx, no dropped arrivals, p95 under 1500ms. Overload ramps 20/60/120 arrivals/s for 15s each: record all admission/rejection/timeouts, never conceal generator saturation. After load stops, every accepted command must exist once and every accepted notification must settle; readiness recovers within 60s, backlog within 120s. These are lab acceptance targets, not a production capacity promise.
- Deployment fault matrix: actual process death after journal intent, runtime file, migrations, service apply, smoke, verified journal, previous inventory, current inventory, and during recovery. A unavailable Docker engine must prevent recovery without advancing current/journal; a subsequent healthy attempt must recover. Bad/corrupt journal must fail closed. No automatic schema downgrade.
- Recovery: source and target are separate hosted Ubuntu jobs, target starts only after source job finishes. Only authenticated encrypted application/partner state and a public inventory leave the source. A repository-scoped Actions secret holds the key independently of the source checkout/VM. Fresh target verifies database counts, private bytes and external operation identity, reconciles ambiguous intents by lookup, and never repeats a remote POST. Lab RPO is zero at the quiescent snapshot; a post-snapshot local marker is intentionally lost. Target RTO ≤ 15 minutes from recovery start (image/bootstrap time included). Wrong key, truncated/tampered archive and missing private object must block activation. This is VM-loss recovery using GitHub's failure domain, not independent-provider disaster recovery, PITR or production HA. Partner state is separately preserved as a simulator fixture; its continuous availability during the source loss is not claimed.
- User SLIs: fixed 24h cohorts mature by their deadlines; denominator includes failed and unfinished accepted operations, not only completed histograms. Notification ≤30s, validation ≤60s, deployment confirmation ≤120s; initial lab objectives 99%, 99%, 99%. Expose pending/late/failed counts and oldest ages. HTTP 5xx/429 and latency remain process counters; authenticated application responses exclude intentional 4xx validation failures from availability, while 429 remains a separate capacity signal. Missing scrape/DB must be visible. No claim of a measured 30-day SLO.

The budget policy freezes feature changes on exhausted objectives and prioritises recovery, capacity or correctness. The original monolith, external lookup and quiescent snapshots each have costs; demonstrate those costs instead of claiming universal 10/10.
