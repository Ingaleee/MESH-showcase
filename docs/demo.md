# Как показать инженерную часть MESH

Демо рассчитано на 10–15 минут. Начните с работающего продукта на `http://localhost:3200`, затем показывайте доказательства выбранных свойств. Формулируйте условия, при которых они сохраняются.

1. **Договорённость и версии.** В разных browser sessions войдите заказчиком и автором. Опубликуйте бриф, отправьте предложение, измените бриф. Старые условия нельзя выбрать; автор может предложить новые. При выборе создаётся соглашение со snapshot условий. Покажите `Marketplace::AwardProposal`, unique Award и тест реальной гонки двух команд.
2. **Приёмка конкретного результата.** Автор передаёт работу, заказчик принимает её версию. Покажите hash содержимого, immutable Submission и составной FK Acceptance → Submission/Engagement. Объясните, почему изменённый бриф или подставленный ID не меняет принятую договорённость.
3. **Неопределённость внешнего платежа.** Для суммы 1 000,05 ₽ выберите «Списание успешно, ответ потерян». Provider уже закоммитил результат, локальная операция сначала не знает исход. Worker делает lookup с прежним key. Повторное подтверждение не создаёт второй журнал. При комиссии 10% fee = 100,01 ₽, net = 900,04 ₽: арифметика выполняется в integer minor units.
4. **Один commit, несколько систем.** Покажите business transaction с outbox, отдельную queue DB, lease и duplicate consumer. Отказ enqueue не теряет событие; notification effect фиксируется вместе с обработкой delivery. Websocket только сообщает об обновлении. Покажите в Jaeger HTTP span и `mesh.event.consume`; HTTP остаётся источником данных при потере realtime.
5. **Восстановление старой истины.** Выполните restore drill. Snapshot не содержит provider confirmation, reconciliation восстанавливает его до duplicate replay. Объясните, почему нельзя возобновлять payout из старого backup без сверки, и где граница доказанного: локальный drill не является региональным disaster recovery.
6. **Измерение и цена решений.** Откройте [verification](verification.md), [ADR](adr.md) и production benchmark. Покажите условия: маленький dataset, 3 Puma threads, public reads, warmup. Объясните, какие измерения приведут к изменению topology, shared rate limiter, search engine или отдельному service. Не экстраполируйте 30 секунд на месячный SLA.

На обсуждении архитектуры полезны конкретные альтернативы: Read Committed + row locks против глобального Serializable; modular monolith против split services; durable outbox против callbacks; schema/versioned snapshots против event sourcing; narrow Money typing против декларации полной статической типизации Rails. Основание и trigger пересмотра записаны в ADR.

Backend демонстрирует работу с инвариантами, конкурентностью, неопределённостью, эксплуатацией и границами доверия. На review защищайте конкретные решения и их проверенные свойства.
