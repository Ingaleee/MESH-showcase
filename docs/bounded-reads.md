# Ограниченные чтения Ruby API

Проверено 8 октября 2026 в MESH-showcase. Marketplace::ProposalPage и Engagements::HistoryPage отделяют чтение от команд изменения состояния.

## Поведение

Предложения: 20 записей по умолчанию, максимум 40. Поиск проверяет имя, сообщение, headline, bio и навыки автора во всей коллекции проекта. Profile IDs остаются SQL subquery, без выгрузки всех профилей в Ruby. Сортировки: новые, цена, срок; одинаковые значения разрешаются created_at/id. Избранные: до 100 UUID; пустой список означает пустую выдачу.

Владелец видит предложения своего проекта; автор — только собственные. Авторизация предшествует чтению истории работы. Signed cursor привязан к actor, project, фильтрам и версии брифа, действует 30 минут и ограничен 2 KiB. Чужой/изменённый/истёкший cursor получает INVALID_CURSOR. Cursor — позиция, не замена авторизации.

Версии: 20, максимум 40. Комментарии: 50; дополнительно возвращаются решения «требуются изменения» для загруженных версий, максимум 40. Благодаря этому свежие комментарии не скрывают старое решение по текущей версии. Следующие страницы версий и комментариев имеют разные cursors. Список рабочих проектов не загружает вложенные истории. События владельца ограничены последними 50, это явно написано в интерфейсе.

Frontend делает серверный поиск с debounce, загружает следующие страницы по запросу пользователя и защищается от устаревшего ответа. Загруженные карточки остаются в cache для drawer/сравнения. Это не лимит общего числа записей, которые пользователь может накопить за сессию.

## Измерение

[50 000 предложений одному проекту](evidence/bounded-read-benchmark.json), пять диагностических samples после warmup:

| Метрика | Прежнее чтение | Страница 20 |
|---|---:|---:|
| Медиана Ruby read | 3 276,624 ms | 27,338 ms |
| Загружено Proposal records | 50 000 | 20 |
| Ruby allocations, типичный sample | 3 750 982 | 3 135 |
| Размер JSON | 31 831 753 bytes | 12 739 bytes |
| SQL SELECT | 3 | 5 |

Дополнительные COUNT стоят запросов, зато payload и Ruby materialization ограничены. JSON size измерен отдельно; его сериализация не включена в read_ms. Это warm local Ruby/PostgreSQL diagnostic: без сети, TLS, frontend, production capacity или RSS claim.

## Границы и цена

Точные counts и substring search всё ещё могут сканировать много строк. Новые composite B-tree indexes ускоряют порядок/позицию, но не делают каждый запрос O(1). Поиск по профилям и skills требует отдельного измерения; поддерживать ещё один search document пока дороже имеющейся задачи.

Страницы не образуют единый snapshot: новые записи, изменение фильтруемых полей или состояния между запросами могут менять результат. Неизменяемые submissions и зафиксированные условия защищаются отдельно в DB; cursor не создаёт эту гарантию.

CONCURRENTLY migrations уменьшают блокирование writes, но требуют времени, места, WAL и контроля незавершённого индекса. Rollback приложения не удаляет эти индексы.

[Регрессии](../apps/api/spec/requests/bounded_reads_spec.rb) проверяют tied ordering без потерь/дубликатов, поиск вне первой страницы, profile skills/bio, actor/filter binding, LIMIT в materializing SQL и сохранение decisions под большим числом комментариев.
